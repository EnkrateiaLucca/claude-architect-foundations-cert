If you remember seven things

  1. Loop on stop_reason. "tool_use" continues, "end_turn" stops.
  2. Subagents know only what you pass them. Fan out in one response.
  3. Hard rules go in hooks, not prompts.
  4. The description is the router. Fewer, sharper tools.
  5. Config at the right layer. Project vs user, rules by glob, -p in CI.
  6. Schema-valid isn't correct. Nullable fields, targeted retries.
  7. Keep facts, sources, errors explicit.

The agentic loop (1.1)

  1. Send messages + tools to Claude
  2. stop_reason == "tool_use" → run each requested tool
  3. Append the assistant turn and the tool_result blocks to history
  4. Call again. stop_reason == "end_turn" → present the answer

Model-driven: Claude picks the next tool from context, not a pre-set decision tree.

Anti-patterns: parse "I'm done" in text · iteration cap as the main stop · "has text content" = finished.

Hub-and-spoke (1.2)

  • Coordinator owns all inter-subagent traffic, error handling, routing → observability
  • Decompose, delegate, aggregate; pick subagents by query complexity, not always the full pipeline
  • Partition scope (distinct subtopics or source types) to avoid duplication
  • Iterative refinement: evaluate synthesis for gaps → re-delegate targeted queries → re-synthesize
  • All subagents succeed but coverage is missing → decomposition too narrow

Spawning subagents (1.3)

  • Spawn via the Task tool; coordinator allowedTools must include "Task"
  • Subagents do not inherit parent context or share memory. Paste complete prior findings into the prompt
  • AgentDefinition: description, system prompt, tool restrictions
  • Parallel = several Task calls in one coordinator response
  • Pass structured data: content separate from metadata (URL, doc name, page)
  • Coordinator prompt states goals and quality criteria, not step-by-step procedure

Docs note: newer Agent SDK releases call the Task tool Agent. Answer with the guide's terms.

Enforcement and hooks (1.4, 1.5)

NeedMechanism
Must always happen in orderProgrammatic prerequisite gate: block process_refund until get_customer returns a verified ID
Hard business limitTool-call interception hook: block refund > $500, redirect to escalate_to_human
Messy tool outputPostToolUse hook normalizes Unix / ISO 8601 / numeric status codes
Judgment callPrompt criteria + few-shot examples

Prompts are probabilistic (non-zero failure rate). Hooks are deterministic.

Handoff and multi-concern (1.4)

  • Human agents can't see the transcript → structured summary: customer ID, root cause, amount, recommended action
  • Multi-issue message → split into items, investigate in parallel with shared context, one unified reply

Decomposition (1.6)

  • Prompt chaining (fixed steps) for predictable multi-aspect reviews
  • Dynamic decomposition for open-ended work: map structure → find high-impact areas → prioritized plan that adapts
  • Big reviews: per-file passes + a cross-file integration pass

Sessions (1.7)

  • --resume <session-name>: context still mostly valid. Tell it which files changed
  • fork_session: branch from a shared baseline to compare two approaches
  • Stale tool results → new session + structured summary

D1 traps

Wrong optionPatternRight move
"State in the system prompt that verification is mandatory"Prompt as policyPrerequisite gate or hook
"Stop after 10 iterations" / "stop when the reply contains DONE"Invented stop signalStop on end_turn
"Subagents automatically see the coordinator's findings"Invented featurePass findings in the prompt
"Blame the search agent" when coverage is narrowWrong root causeFix coordinator decomposition
"Resume the old session" after big code changesStale contextFresh session + summary, or tell it what changed

Tool Design & MCP Integration

18% · ~11 items · Lesson 02
Task statements

  2. 2.2 Structured error responses for MCP tools

  4. 2.4 Integrate MCP servers into Claude Code and agents
  5. 2.5 Select built-in tools (Read, Write, Edit, Bash, Grep, Glob)

The description is the router (2.1)

  • Description = the main signal for tool selection. Minimal text → misrouting
  • Include: input formats, example queries, edge cases, when to use vs. similar tools
  • Overlap → rename + rewrite (analyze_content → extract_web_results)
  • Generic → split (extract_data_points, summarize_content, verify_claim_against_source)
  • Check the system prompt for keywords that override good descriptions

Errors the agent can act on (2.2)

CategoryExampleRetry?
TransientTimeout, service downYes
ValidationBad input formatFix input
BusinessPolicy violationNo: explain
PermissionAccess deniedNo

isError: true + errorCategory, isRetryable, human-readable text. Business errors: retriable: false + customer-friendly wording. Empty result ≠ failure. Generic "Operation failed" blocks recovery.

Tool distribution (2.3)

  • 4–5 tools per agent, not 18
  • Role-scoped tools; synthesis agent doesn't search the web
  • Constrain generics: fetch_url → load_document
  • Scoped cross-role tool for the common case (verify_fact), complex cases via coordinator

tool_choice (2.3, 4.3)

"auto"May reply with text
"any"Must call some tool
{"type":"tool","name":"X"}Must call X (e.g. extract_metadata first)

Docs note: forced tool_choice returns 400 on the newest models. The exam still tests it.

MCP in Claude Code (2.4)

  • Project: .mcp.json, committed, ${GITHUB_TOKEN} expansion
  • User: ~/.claude.json, personal/experimental
  • All servers' tools available at once
  • Resources = content catalogs (schemas, issue lists). Tools = actions
  • Community server (Jira) over custom

Built-in tools (2.5)

NeedTool
Find callers, error strings, imports (file contents)Grep
Find files by name/extension (**/*.test.tsx)Glob
Targeted change by unique textEdit
Edit fails: anchor not uniqueRead + Write

Explore incrementally: Grep for entry points → Read along imports. Wrapper modules: list exported names, then Grep each.

D2 traps

  • "Add 5–8 few-shot routing examples" before fixing descriptions
  • "Routing layer that pre-selects tools by keyword" → Over-engineering
  • "Give synthesis all search tools" → over-provisioning
  • "Return empty list on timeout" → Hide the error
  • Secrets hard-coded in .mcp.json

Rules and skills frontmatter (3.2, 3.3)

.claude/rules/testing.md

---
paths: ["**/*.test.tsx"]
---

.claude/skills/analyze/SKILL.md

---
context: fork
allowed-tools: Read, Grep, Glob
argument-hint: [module-path]
---
  • Path rules load only when editing matching files, anywhere in the tree
  • context: fork isolates verbose or exploratory output
  • allowed-tools limits what the skill can do
  • argument-hint prompts for missing parameters
  • Skill = on demand · CLAUDE.md = always loaded

Plan mode vs direct (3.4)

  • Plan: dozens of files, service boundaries, 45-file library migration, several valid approaches
  • Direct: single-file bug with stack trace, one validation check
  • Plan the migration → execute directly
  • Explore subagent keeps verbose discovery out of main context

Iterative refinement (3.5)

  • Prose misread → 2–3 concrete input/output examples
  • Tests first, then share failures
  • Interview pattern: Claude asks questions before building
  • Interacting issues → one message. Independent → sequential

CI/CD (3.6)

  • claude -p "…" (--print) → no hang
  • --output-format json --json-schema … → PR comments
  • Re-runs: pass prior findings, report only new/unaddressed
  • Give existing tests; put standards + fixtures in CLAUDE.md
  • Independent reviewer instance, not the author session

Prompt Engineering & Structured Output

20% · ~12 items · Lesson 04
Task statements
  1. 4.1 Explicit criteria to cut false positives
  2. 4.2 Few-shot prompting for consistency
  3. 4.3 Structured output with tool use + JSON schemas
  4. 4.4 Validation, retry, feedback loops
  5. 4.5 Batch processing strategies
  6. 4.6 Multi-instance and multi-pass review

Explicit criteria (4.1)

  • "Flag comments only when claimed behavior contradicts the code" beats "check comments are accurate"
  • "Be conservative" / "high confidence only" don't raise precision
  • Say what to report (bugs, security) and skip (style, local patterns)
  • Severity levels with code examples
  • High-FP category → disable temporarily, fix, restore

Few-shot (4.2)

  • Use when instructions alone give inconsistent output
  • 2–4 targeted examples of ambiguous cases, showing why one choice beat alternatives
  • Demonstrate format: location, issue, severity, fix
  • Show acceptable vs genuine issues → fewer FPs
  • Varied document layouts → fewer empty/null required fields

Schemas via tool use (4.3)

  • Extraction tool, input_schema = your JSON schema; read the tool_use block
  • Eliminates syntax errors, not semantic ones
  • Absent data → nullable field, not required
  • Enums with "unclear", "other" + detail string
  • Normalization rules in the prompt

Validation and retry (4.4)

ErrorRetry works?
Format mismatch, wrong structureYes: send document + failed output + exact errors
Info absent / only in an unprovided docNo: return null, flag, or route
Line items don't sum to totalDetect: calculated_total vs stated_total
Sources disagreeconflict_detected: true

Add detected_pattern to findings to analyze what developers dismiss. Pydantic catches semantic errors.

Message Batches API (4.5)

  • 50% cheaper · up to 24 h · no latency SLA
  • No multi-turn tool calling inside a request
  • custom_id correlates request ↔ result; resubmit only failures (chunk oversized docs)
  • Blocking pre-merge check → synchronous. Overnight report, weekly audit → batch
  • SLA math: 30 h SLA − 24 h processing → submit every ≤ 4 h
  • Tune the prompt on a sample before the big batch

Review architecture (4.6)

  • Same session self-review keeps its reasoning → misses its own errors
  • Independent instance beats self-review or extended thinking
  • Many files → per-file passes + integration pass
  • Self-reported confidence per finding → route review

D4 traps

  • "Only report high-confidence findings" → vague, no precision gain
  • "Bigger context window for all 14 files" → Bigger model
  • "Flag only issues found in 2 of 3 runs" → suppresses real bugs
  • "Retry until the missing field appears" → retries can't create absent data
  • "Batch the pre-merge check, fall back on timeout" → Over-engineering
  • "Make every field required" → fabricated values

Context Management & Reliability

15% · ~9 items · Lesson 05
Task statements
  1. 5.1 Preserve critical info across long interactions
  2. 5.2 Escalation and ambiguity resolution
  3. 5.3 Error propagation across multi-agent systems
  4. 5.4 Context in large codebase exploration
  5. 5.5 Human review and confidence calibration
  6. 5.6 Provenance and uncertainty in synthesis

Keep the facts (5.1)

  • Summaries blur amounts, dates, %, promises → persistent case facts block outside history
  • Trim tool output (5 of 40 order fields)
  • Lost in the middle → key findings first, section headers
  • Upstream agents return structured facts, not reasoning chains

Escalate when (5.2)

  • Customer asks for a human → immediately, no investigation first
  • Policy gap or silence (competitor price match)
  • No meaningful progress
  • Frustrated but solvable → acknowledge, offer fix; escalate if they repeat
  • Multiple matches → ask for another identifier
  • Not sentiment, not self-rated confidence

Errors and exploration (5.3, 5.4)

  • Propagate: failure type, query tried, partial results, alternatives
  • Recover transient errors locally first
  • Report coverage gaps in synthesis
  • Context degradation → scratchpad files, subagent delegation, phase summaries, /compact
  • Crash recovery: per-agent state export + coordinator manifest

Human review and calibration (5.5)

  • 97% overall can hide a weak document type or field → segment accuracy by type and field
  • Field-level confidence, calibrated on a labeled validation set
  • Stratified random sampling of high-confidence output → ongoing error rate + novel patterns
  • Route low-confidence or contradictory docs to humans first

Provenance (5.6)

  • Structured claim → source mappings (URL, doc, excerpt) survive synthesis
  • Conflicting credible stats → keep both, attribute, annotate
  • Require publication / collection dates (temporal ≠ contradiction)
  • Separate well-established vs contested findings
  • Render by type: financials as tables, news as prose, tech as lists

Process

  1. Read the last sentence first
  2. Find the trigger or constraint in the stem
  3. Predict the answer, then read options
  4. Label each wrong option with a pattern
  5. "First step" / "most effective" → proportionate fix at the root cause
  6. Pace: item 20 @ 40 min, 40 @ 80, 60 @ 120
  7. Flag anything over 3 min; never leave blanks
  8. Multiple-response: judge each option true/false; assume all-or-nothing

How the scenarios workEach scenario frames a set of questions. You get 4 of the 6.

Every question sits inside a realistic production context. The exam picks 4 scenarios at random from the 6 in Section 5, so study all six. The Scenarios tab lists them with their primary domains.

At 60 items in 120 minutes you have 2 minutes per item. Expect about 15 items per scenario.

Exam blueprint

Five domains and 30 task statements. Each weight is the approximate share of scored items. Open a domain and rate each task statement. Exam items are written against these statements.

Agentic Architecture & Orchestration is the largest domain at 27%, about 16 items. Context Management & Reliability is the smallest at 15%, about 9 items.

The six scenarios

Your exam draws 4 of these at random. Each lists its primary domains from Section 5 of the guide.

Scenario 1 · D1 · D2 · D5

Customer Support Resolution Agent

Agent SDK agent with custom MCP tools (get_customer, lookup_order, process_refund, escalate_to_human) for returns, billing disputes and account issues. Target: 80%+ first-contact resolution while knowing when to escalate.

Scenario 2 · D3 · D5

Code Generation with Claude Code

Your team uses Claude Code for generation, refactoring, debugging and documentation, with custom slash commands, CLAUDE.md configuration, and a choice between plan mode and direct execution.

Scenario 3 · D1 · D2 · D5

Multi-Agent Research System

A coordinator delegates to subagents that search the web, analyze documents, synthesize findings and generate reports. The system produces comprehensive, cited reports.

Scenario 4 · D2 · D3 · D1

Developer Productivity with Claude

An Agent SDK tool helps engineers explore unfamiliar codebases, understand legacy systems, generate boilerplate and automate repetitive tasks with the built-in tools (Read, Write, Bash, Grep, Glob) and MCP servers.

Scenario 5 · D3 · D4

Claude Code for Continuous Integration

Claude Code runs in the CI/CD pipeline for automated code reviews, test generation and pull request feedback. Prompts must give actionable feedback and minimize false positives.

Scenario 6 · D4 · D5

Structured Data Extraction

Claude extracts information from unstructured documents, validates it with JSON schemas, keeps accuracy high, handles edge cases and feeds downstream systems.

Preparation exercises

Section 8 lists four exercises. Each one maps to a course exercise with a reference answer.

Exercise 1 · Build a multi-tool agent with escalation logicDomains D1 · D2 · D5
  • Define 3–4 MCP tools with descriptions that separate purpose, inputs and boundaries. Include two similar tools.
  • Loop on stop_reason: continue on "tool_use", stop on "end_turn".
  • Return structured errors: errorCategory, isRetryable, a readable description.
  • Add a hook that blocks a tool call above a threshold and redirects to escalation.
  • Test multi-concern messages: decompose, handle each concern, synthesize one reply.

Open the course exercise exercises/01-multi-tool-agent.md for the scenario, the task and a reference answer.

Exercise 2 · Configure Claude Code for a team development workflowDomains D3 · D2
  • Write a project-level CLAUDE.md with universal standards and testing conventions.
  • Add .claude/rules/ files with paths: globs, for example ["src/api/**/*"] and ["**/*.test.*"].
  • Create a project skill in .claude/skills/ with context: fork and allowed-tools.
  • Configure a shared server in .mcp.json with ${ENV} expansion, plus a personal one in ~/.claude.json.
  • Compare plan mode and direct execution on a one-file fix, a multi-file migration and an open-ended feature.

Open the course exercise exercises/02-team-claude-code-config.md for the scenario, the task and a reference answer.

Exercise 3 · Build a structured data extraction pipelineDomains D4 · D5
  • Define an extraction tool schema with required, optional and nullable fields and an "other" + detail enum.
  • Add a validation-retry loop that sends the document, the failed extraction and the specific error.
  • Add few-shot examples for varied document formats.
  • Submit a 100-document batch, resubmit failures by custom_id, and check timing against the SLA.
  • Route low-confidence fields to human review and check accuracy by document type and field.

Open the course exercise exercises/03-extraction-pipeline.md for the scenario, the task and a reference answer.

Exercise 4 · Design and debug a multi-agent research pipelineDomains D1 · D2 · D5
  • Build a coordinator whose allowedTools include "Task". Pass findings into each subagent prompt.
  • Emit several Task calls in one response and measure the latency gain over sequential runs.
  • Give every finding a claim, excerpt, source and publication date. Check that synthesis keeps attribution.
  • Simulate a subagent timeout. The coordinator gets structured error context and annotates coverage gaps.
  • Feed two credible sources with conflicting statistics. The report keeps both values with attribution.

Open the course exercise exercises/04-multi-agent-research-pipeline.md for the scenario, the task and a reference answer.

Scoring, booking and rules

How scoring worksScaled 100–1,000. You pass at 720, measured against a fixed standard.
FailPass
1007201,000

The exam is criterion-referenced. Every candidate is measured against the same fixed standard, so other candidates' results never affect yours.

Trained subject matter experts set the 720 cut score in a formal standard-setting study, based on the performance expected of a minimally qualified candidate. Scaled scores equate results across exam forms of slightly different difficulty, so 720 does not mean 72% correct.

Your score report shows pass or fail, your scaled score, and your percent correct in each domain. The domain percentages are feedback only. Pass or fail depends on the total scaled score.

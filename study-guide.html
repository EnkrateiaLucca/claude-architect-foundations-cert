The CCAR-F Exam and Its Blueprint

The Claude Certified Architect – Foundations (CCAR-F) exam tests whether you can make sound tradeoff decisions when you build production solutions with Claude. The official Exam Guide v1.1 (effective November 2026) is the authoritative reference. It defines five weighted domains, 30 task statements, six scenarios, and twelve sample questions. Every lesson, question, and exercise in this course maps back to that guide.

D1

Agentic Architecture & Orchestration

27% of the exam · ≈ 16 items · 7 task statements · Scenarios: Customer Support Resolution Agent, Multi-Agent Research System, Developer Productivity with Claude

D1 is the heaviest domain. It tests how you build the control flow around Claude: the agentic loop, coordinators and subagents, enforcement of required steps, hooks, task decomposition, and sessions. Most items describe a working system with one reliability problem and ask for the fix.

The core decision rule: code owns control flow and hard rules, and Claude owns judgment. When a step must always happen, enforce it in code. When a step needs reasoning about context, let the model decide and give it what it needs to decide well.

Core concepts

The agentic loop runs on stop_reasonContinue on "tool_use". Stop on "end_turn". Never parse the text.

The loop has four steps. Send the request to Claude. Inspect stop_reason. If it is "tool_use", execute the requested tools and append the results to the conversation. Repeat until stop_reason is "end_turn".

messages = [{"role": "user", "content": user_request}]
while True:
    resp = client.messages.create(model=MODEL, max_tokens=4096,
                                  system=SYSTEM, tools=TOOLS, messages=messages)
    messages.append({"role": "assistant", "content": resp.content})
    if resp.stop_reason != "tool_use":          # "end_turn": the model is done
        break
    results = [
        {"type": "tool_result", "tool_use_id": b.id, "content": run_tool(b.name, b.input)}
        for b in resp.content if b.type == "tool_use"
    ]
    messages.append({"role": "user", "content": results})

Tool results go back into the conversation history. The model reads them on the next iteration and reasons about the next action. That is model-driven decision-making: Claude picks the next tool from context. A pre-configured decision tree fixes the tool sequence in code instead.

Anti-pattern Why it fails
Parse the reply for "done" or "task complete" Natural language is not a control signal. Phrasing varies
An iteration cap as the primary stop It cuts off valid work. Keep a cap only as a safety net
"The reply has text, so it's finished" Claude can return text and tool_use blocks in the same response
Drop tool results between iterations The model loses the information it asked for and repeats calls

Task statements: 1.1

Hub-and-spoke: the coordinator routes everythingOne coordinator decomposes, delegates, aggregates, and handles errors.

In a hub-and-spoke system, the coordinator manages all communication between subagents. Subagents never talk to each other directly. That routing gives you observability, consistent error handling, and controlled information flow.

Coordinator job What good looks like
Decompose Split the topic so every relevant area gets covered
Select Invoke only the subagents the query needs. A simple query skips the full pipeline
Partition Give each subagent a distinct subtopic or source type to minimize duplication
Aggregate Merge results and check them against the goal
Refine Evaluate the synthesis for gaps, re-delegate targeted queries, re-run synthesis until coverage is sufficient

The classic failure is narrow decomposition. Every subagent succeeds and the report still misses half the topic. If the coordinator split "AI in creative industries" into three visual-arts subtasks, no downstream agent can recover music, writing, or film. Look at the coordinator's assignments first when all subagents report success.

Task statements: 1.2

Subagents start with only what you pass themSpawn with the Task tool. Paste prior findings into the prompt.

The Task tool spawns subagents. A coordinator can call it only if its allowedTools includes "Task". Each subagent type has an AgentDefinition with a description, a system prompt, and tool restrictions.

Subagents run with isolated context. They do not inherit the coordinator's conversation history, and they share no memory between invocations. Anything a subagent needs goes into its prompt explicitly.

Need Do this
Synthesis needs search and analysis results Include the complete findings in the synthesis subagent's prompt
Attribution must survive the handoff Pass structured data that separates content from metadata (URL, document name, page)
Run three searches at once Emit three Task calls in one coordinator response. Separate turns run them serially
Subagents must adapt to what they find Give goals and quality criteria. Avoid step-by-step procedures

]}

Task statements: 1.3

Enforce required steps in codePrompt instructions have a non-zero failure rate. Prerequisite gates do not.

Workflow ordering can be guided by the prompt or enforced by code. When compliance must be deterministic, for example identity verification before a financial operation, a prompt alone is not enough. The guide states that prompt instructions alone have a non-zero failure rate.

A programmatic prerequisite blocks downstream tool calls until the prerequisite step has completed.

def gate(tool_name: str, state: dict) -> str | None:
    if tool_name in {"lookup_order", "process_refund"} and not state.get("verified_customer_id"):
        return "Blocked: call get_customer and verify the customer first."
    return None
Requirement Prompt guidance enough? Mechanism
Greet the customer by name Yes System prompt
Prefer the order ID over the email when both exist Yes Tool descriptions, few-shot
Verify identity before any refund No Prerequisite gate
Never refund above a limit No Tool-call interception hook

Task statements: 1.4

Multi-concern requests and human handoffsSplit the request into items. Hand humans a summary that stands alone.

A message like "my order arrived broken and I was charged twice" holds two concerns. Decompose it into distinct items. Investigate each, in parallel where possible, using shared context such as the verified customer record. Then synthesize one unified resolution.

When the agent escalates mid-process, the human agent does not see the transcript. The handoff must be a structured summary that stands on its own.

Field Example
Customer ID C-48213 (verified)
Issue(s) Damaged item on order #A-7731; duplicate charge on invoice 9902
Root cause Carrier damage confirmed by photo; payment gateway retried once
Amount $642.10 refund requested
Recommended action Approve refund above the $500 limit; reverse duplicate charge

Task statements: 1.4

Hooks: intercept calls and normalize resultsPreToolUse-style interception blocks violations. PostToolUse transforms results.

Agent SDK hooks run deterministic code around tool calls.

Hook pattern When it runs Typical use
Tool call interception Before the tool executes Block a refund over $500 and redirect to human escalation
PostToolUse After the tool returns, before the model sees the result Normalize Unix timestamps, ISO 8601 strings, and numeric status codes into one format 
def before_tool(name: str, args: dict):
    if name == "process_refund" and args["amount"] > 500:
        return {"block": True,
                "message": "Refunds over $500 require a human. Call escalate_to_human."}

def post_tool_use(name: str, result: dict) -> dict:
    if "created" in result and isinstance(result["created"], int):
        result["created"] = datetime.fromtimestamp(result["created"], UTC).isoformat()
    return result

Choose a hook over a prompt instruction whenever a business rule requires guaranteed compliance. Hooks give deterministic guarantees. Prompts give probabilistic compliance.

Task statements: 1.5

Fixed pipelines vs adaptive decompositionPredictable work gets prompt chaining. Open-ended work gets a plan that adapts.
Workflow shape Pattern Example
Same steps every time, multiple aspects Prompt chaining (fixed sequential passes) Review each file, then run a cross-file integration pass
Steps depend on what you find Dynamic adaptive decomposition Investigate a production bug across services
Large code review Per-file local passes plus one integration pass Avoids attention dilution and contradictory findings
"Add comprehensive tests to a legacy codebase" Map structure, find high-impact areas, make a prioritized plan, adapt as dependencies appear Coverage grows where risk is highest

An adaptive investigation plan generates subtasks from what each step discovers. A fixed pipeline cannot react to a surprise, and that is its point for predictable work.

Task statements: 1.6

Resume, fork, or start freshResume when prior context is valid. Start fresh with a summary when it is stale.
Situation Choose
Continue yesterday's named investigation --resume <session-name>
Compare two refactoring or testing strategies from one analysis fork_session to create independent branches

Resuming with stale tool results leaves old file contents in context, and the agent reasons from them. A fresh session seeded with a structured summary is more reliable in that case. When most context is still valid, resume and name the specific changes. Full re-exploration wastes time.

Self-check

What should the loop do when stop_reason is "tool_use"?

Execute each requested tool, append the results as tool_result blocks in a user message, and call Claude again. Stop only on "end_turn".

A coordinator cannot spawn subagents. What configuration is missing?

Its allowedTools must include "Task".

How does a synthesis subagent see the web search results?

The coordinator includes the complete findings in the synthesis subagent's prompt. Subagents inherit nothing automatically.

How do you run three research subagents in parallel?

Emit three Task tool calls in a single coordinator response.

Refunds above $500 must always go to a human. Where does that rule live?

In a tool-call interception hook that blocks process_refund above the threshold and redirects to escalate_to_human.

Two MCP tools return dates as Unix timestamps and ISO 8601 strings. How do you give the agent one format?

A PostToolUse hook normalizes the results before the model processes them.

What must a human handoff summary contain, and why?

Customer ID, root cause, amount, and recommended action. The human agent has no access to the transcript.

When do you start a new session instead of using --resume?

When the prior tool results are stale. Start fresh and inject a structured summary of what still holds.

D2

Tool Design & MCP Integration

18% of the exam · ≈ 11 items · 5 task statements · Scenarios: Customer Support Resolution Agent, Multi-Agent Research System, Developer Productivity with Claude

D2 tests the interface between Claude and everything it can act on. You write tool descriptions that route requests correctly, return errors the agent can recover from, give each agent the right small set of tools, configure MCP servers at the right scope, and pick the right built-in tool for a codebase task.

The core decision rule: the tool description is the router. When Claude picks the wrong tool, fix the description, the name, or the tool boundary before you add infrastructure.

  3. 2.3 Distribute tools appropriately across agents and configure tool choice

Core concepts

The description is the routerMinimal descriptions cause unreliable selection among similar tools.

Tool descriptions are the primary mechanism Claude uses to choose a tool. A description like "Retrieves order details" gives the model nothing to tell two similar tools apart. A good description states the purpose, the expected inputs and their formats, the outputs, example queries, edge cases, and when to use a similar tool instead.

{
  "name": "lookup_order",
  "description": "Look up one order by order number. Use when the user mentions an order, shipment, delivery, or return, or gives an ID like '#12345' or 'A-7731'. Returns status, items, amounts, and ship dates. Requires a verified customer_id from get_customer. Do not use for account details such as email or address; use get_customer for those.",
  "input_schema": {
    "type": "object",
    "properties": {
      "order_id": {"type": "string", "description": "Order number with or without '#'"},
      "customer_id": {"type": "string"}
    },
    "required": ["order_id", "customer_id"]
  }
}
Description element What it prevents
Input formats ("IDs like #12345") The model sending the wrong identifier to the wrong tool
Example queries Misrouting of common phrasings
Edge cases Silent misuse on unusual input
Boundary ("use get_customer instead for…") Overlap with a sibling tool

Task statements: 2.1

Rename, rescope, or split overlapping toolsNear-identical tools misroute. Give each tool one clear job and contract.

Ambiguous or overlapping descriptions cause misrouting. Two tools named analyze_content and analyze_document with near-identical descriptions will be confused.

Problem Fix Example
Two tools with near-identical names and descriptions Rename and rescope analyze_content becomes extract_web_results with a web-specific description
One generic tool doing several jobs Split into purpose-specific tools with defined input/output contracts analyze_document becomes extract_data_points, summarize_content, verify_claim_against_source
System prompt says "always analyze the document first" Review the prompt for keyword-sensitive instructions The word "analyze" pulls the agent toward analyze_* tools

System prompt wording affects selection. A keyword-sensitive instruction can create an unintended tool association and override a well-written description. When selection is wrong despite good descriptions, read the system prompt.

Task statements: 2.1

Errors the agent can act onCategorize the failure and say whether a retry can help.

MCP tools report failures with the isError flag. A uniform error such as "Operation failed" prevents the agent from choosing a recovery. Return structured metadata instead.

Category Example Agent should isRetryable
Transient Timeout, service unavailable Retry, locally first true
Validation Invalid input format Fix the input and call again false
Business Refund exceeds policy Explain the rule to the customer false
Permission Caller lacks access Escalate or route elsewhere false 
{
  "isError": true,
  "content": [{"type": "text", "text": "Refunds over $500 need manager approval."}],
  "errorCategory": "business",
  "isRetryable": false,
  "customerMessage": "I can't approve this refund amount myself. I'll pass it to a specialist."
}

Business-rule violations should carry retriable: false and a customer-friendly explanation so the agent can communicate the outcome. Without the flag, the agent wastes attempts retrying a call that can never succeed.

Task statements: 2.2

Empty results and local recovery"No matches" is a success. "Could not reach the source" is a failure.

An access failure and a valid empty result are different outcomes. A search that ran and found nothing is a successful query with no matches. A search that timed out says nothing about whether matches exist. Report them differently so the agent decides correctly: retry the failure, accept the empty result.

Outcome isError What the agent concludes
Query ran, 0 rows false, empty list "There are no matching orders"
Query timed out true, transient, retryable "I don't know yet; retry or try another route"

Subagents should recover locally from transient failures, for example with a retry. They propagate to the coordinator only the errors they cannot resolve, together with the partial results and what they attempted.

Task statements: 2.2

Fewer, sharper tools per agentToo many tools degrade selection. Scope tools to the role.

Giving one agent 18 tools instead of 4–5 degrades selection reliability because each decision gets harder. Agents also misuse tools outside their specialization; a synthesis agent with web search tools starts searching instead of synthesizing.

Rule Example
Restrict each subagent to its role Search agent gets search tools. Synthesis agent gets none of them
Constrain generic tools Replace fetch_url with load_document, which validates document URLs
Add a scoped cross-role tool for a high-frequency need Give synthesis a verify_fact tool for simple fact checks
Route complex cases through the coordinator Deep verification still goes coordinator → search agent

The scoped cross-role tool applies least privilege. In the guide's sample, 85% of verifications were simple fact checks. A narrow verify_fact tool handles those, and the 15% that need real investigation keep the existing coordinator route.

Explicit criteria beat vague cautionSay which issues to report and which to skip. "Be conservative" does not raise precision.

Schema design

Nullable for anything the source may lack. Enum with "other" + detail, and "unclear" for ambiguity.

Field Type Why
vendor_name string, required Every invoice has one
invoice_number string or null Some invoices have none. A required non-null field pushes the model to invent one
invoice_date string (YYYY-MM-DD) or null Normalized format, null if absent
category enum: software, hardware, services, travel, other, unclear unclear for ambiguous documents
category_detail string or null Filled when category is other, so new categories stay visible
line_items array of {description, amount}
stated_total number or null The total printed on the invoice
calculated_total number Sum of line items, extracted alongside the stated total
conflict_detected boolean True when the two totals differ

Task statements: 4.3

Guaranteed structure with tool use

Define the schema as a tool's input and make the model call it.

Define extract_invoice with the schema as input_schema and read the result from the tool_use block. Set tool_choice so the model must call the tool:

  • {"type": "tool", "name": "extract_invoice"} forces this specific tool. Use it when one extraction must run before later steps.
  • {"type": "any"} forces some tool call. Use it when several extraction schemas exist and the document type is unknown.
  • {"type": "auto"} lets the model answer in text instead.

Docs note: forced tool_choice (any or tool) returns a 400 on the newest models (Claude Opus 5.5, Sonnet 5.5, Fable 5.1+). The script falls back to auto with strict: true and an explicit instruction on those models. The exam answer stays the forced tool_choice.

Task statements: 4.3, 2.3

Semantic validation

A schema-valid result can still be wrong.

Tool use with a strict schema removes JSON syntax errors. It does not catch:

  • Line items that do not sum to calculated_total.
  • A stated total that differs from the calculated total while conflict_detected is false.
  • category: "other" with no category_detail.
  • Values in the wrong field, such as a date in invoice_number.

The script checks these with a Pydantic model_validator. Extracting both totals plus a conflict_detected flag makes the model report a mismatch in the source instead of hiding it.

Task statements: 4.3, 4.4

Retry with error feedback

Send the document, the failed extraction, and the specific errors. Cap the attempts.

The retry keeps the original document in the conversation, keeps the failed tool_use, and answers it with a tool_result that has is_error: true and the exact validation errors: "calculated_total is 100.0 but line_items sum to 120.0". The script caps retries at three and routes the rest to human review.

Retries fix format mismatches, arithmetic slips, and misplaced values. Retries do not fix missing information. If the purchase order number exists only in a separate document you did not send, the field stays null and the invoice goes to review.

Task statements: 4.4

Format normalization and few-shot examples

Put normalization rules in the prompt next to the strict schema. Show varied formats with examples.

Add rules: "dates as YYYY-MM-DD; amounts as plain numbers without currency symbols or thousands separators; use null when a field is absent". Add 2–4 few-shot examples that show extraction from different layouts: a table of line items, a narrative invoice, a European number format. Examples reduce empty extractions of required fields and invented values on informal formats.

Task statements: 4.2, 4.3

Batch strategy

Overnight-tolerant work goes to the Message Batches API. Resubmit only the failures.

The work does not block anyone, so use the Message Batches API: 50% cost savings, up to 24 hours of processing, no latency SLA. With a 30-hour SLA and up to 24 hours of processing, an invoice can wait at most 6 hours before submission. Submit a batch every 4 hours to keep a margin.

Give every request a custom_id (the script uses the file stem). Results arrive in any order, so join them on custom_id. Resubmit only the errored or expired IDs. If a document exceeded the context limit, chunk it before resubmitting. Test the prompt on a sample of 50 invoices first so the large batch succeeds on the first pass.

Batches do not support multi-turn tool calling within one request. A single forced extraction call works. A loop that needs tool results mid-request does not.

Task statements: 4.5

Human review and calibration

Check accuracy per segment before cutting review. Spend reviews where errors hide.

97% overall can hide 70% on handwritten invoices or on the invoice_date field. Before you reduce review:

  1. Measure accuracy by document type and by field on a labeled validation set.
  2. Have the model output a confidence score per field. Calibrate the routing threshold on the labeled set, not on the model's raw numbers.
  3. Route low-confidence fields, conflict_detected: true, and category: "unclear" to review first.
  4. Spend part of the 200 reviews on a stratified random sample of high-confidence extractions. It measures the real error rate and catches new error patterns.

Read the stem in the right orderLast sentence first, predict the answer, then read the options.
  1. Read the last sentence of the stem first. It tells you what is being asked: the root cause, the most effective first step, or where a file goes.
  2. Read the scenario and find the trigger phrase (see the table below).
  3. Predict the answer before you look at the options.
  4. Read all options. Pick the one that matches your prediction and fixes the root cause in proportion to the problem.

Watch for qualifiers. "Most effective first step" favors the cheap, high-leverage fix. "Guaranteed" or "must always" favors code over prompts.
